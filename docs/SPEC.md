Status: Approved 2026-10-03 (user: "set the loop!" in reply to the Draft 1 request, with the defaults in section 6 accepted unless changed later).

They await the user's confirmation at G3 sign-off.

## 1. Purpose

Take one prompt the user wrote, return one more effective prompt that keeps what the user meant.
Search method: GEPA (Agrawal et al., arXiv:2507.19457), reflective prompt evolution with a Pareto
frontier, run through `gepa==0.1.4` `optimize_anything`. Entry points: the `autoimprover` command and
the Claude Code slash command `/improve` (alias `/optimize`).

"Effective" means the prompt's *outputs* score higher on a fixed check set. Wording quality alone
is never the score (that was the 0.1.0 defect).

## 2. Requirements

Each has a proof: a test (T), an acceptance test (A, black-box, written from this spec) or the
user's `just smoke` (S).

### Input and output
- R1. Input is a prompt from an argument, a file (`--file`) or stdin (UTF-8, 1 to 20,000 chars, no NUL character, line endings normalised to LF (so a CRLF prompt and its LF rewrite keep the same literals, R9), and none of GEPA's template tokens `<curr_param>` and `<side_info>`, which its string substitution cannot escape; otherwise exit 2 with a message naming the problem). Proof: T.
- R2. Output is exactly one improved prompt plus a report: scores before/after on the holdout, calls used, a word-level diff, and 3 to 6 lines saying what changed and why. Without `--json` the improved prompt alone goes to stdout (so it can be piped) and the report to stderr; `--json` writes one JSON object with both to stdout. Exit codes: 0 done (including "no reliable improvement"), 1 internal error (stderr also names the run folder and the resume line when a run folder exists), 2 bad input or usage or a refusal before any paid call (R1, R4, R14, R17 fixed costs, R23 state folder), 3 backend failure (R24), 4 session not locked down (R18), 130 interrupted (Ctrl-C). Every non-zero exit writes `error: <what, and the flag or folder to change>` to stderr and nothing to stdout; exits 3 and 130 also print `run folder: <path>` and `resume with: autoimprover --resume <id>`. With `--json` stdout always carries exactly one object (`{"status":"error","code":N,"error":"...","run_dir":"..."}` on errors), and notices stay on stderr. GEPA's own progress output never reaches stdout. The report also says whether the result is holdout-verified and whether the search was cut short by the clock (a search that used its share of the calls is the normal ending, and GEPA never ends a search on its own), plus a fixed `reason_code` and the reason text, so "no reliable improvement" and "ran out before confirming" can be told apart. The full state table is in `docs/ARCHITECTURE.md`. Proof: A.
- R3. If no candidate beats the original on the holdout by more than the measured noise, the original is returned unchanged, the report says "no reliable improvement", and the exit code is 0. Proof: A with the `fake` backend.
- R4. A `--dry` run prints the plan (models, call budget, the fixed costs before and after the search, scenario count, **estimated number of GEPA iterations the budget affords**, the clock share kept for the final steps) and makes zero model calls and writes nothing; once the arguments parse it always exits 0, a usage error still being exit 2 (the iteration estimate counts calls; the 45-minute clock, with live calls of 5 to 45 s, may end the search sooner), and says "a real run would refuse: <reason>" when one would (for any reason, including a state folder that is not usable, R23). A real run whose budget affords fewer than 4 iterations refuses to start unless `--force-low-budget` is given. Proof: A.

### Fidelity: not deviating in ways the user would not like
- R5. Before the search, one call extracts an **intent contract** from the prompt (goal, hard constraints, facts and names to keep, required output format, language, tone) and classifies its **kind**: `template` (a reusable instruction applied to varying inputs: system prompts, skills, slash commands) or `task` (a one-off request, the usual case for prompts typed into Claude Code). `--kind` overrides the guess. The contract is stored in the run folder and shown in the report. Proof: T.
- R6. Every candidate that becomes the answer passes the contract check: all "keep" items present or equivalent, no new goals added, same language and output format. A failing candidate is never returned. Proof: A with planted violations.
- R7. Length cap: the result is at most the strictness cap of R8 times the original's tokens (floor: the original plus 40 tokens, so very short prompts can still gain a sentence); `--allow-growth` removes the cap. The report states the ratio. Proof: T.
- R8. Strictness levels `conservative` (default: minimal edits, structure kept), `balanced`, `bold`. The level sets the reflection instructions and the cap in R7 (1.25x / 1.5x / 2.5x). Proof: T on the prompt templates, S on 5 prompts.
- R9. Placeholders, code blocks, URLs, file paths and quoted strings in the original appear unchanged in the result. Proof: T (a hand-written property test with a seeded random generator; no new dependency).

### Scoring
- R10. Candidates are scored by running them. A task model executes the candidate on each scenario; the output is checked by (a) programmatic checks (format, length, required and forbidden strings from the contract), then (b) a binary checklist derived from the contract and judged by a different model that sees the output and the checklist but not the candidate text. Score = share of checks passed. The judge is called **once per candidate per batch of scenarios** (all outputs and checklists in one call), not once per scenario. The evaluator also returns `side_info["scores"]` with one entry per check group (for example `format`, `constraints`, `content`), which GEPA tracks as separate objectives on the frontier. Proof: T with `fake`.
- R10a. How a candidate is executed (one task call). `template`: the candidate is the system prompt and the scenario input is the user message. `task`: the scenario is a short synthesised *situation* (context the request could arrive in, for example different project details or constraints, never invented facts that contradict the contract) and the task model receives the situation followed by the candidate as the user message, with no system prompt. Single-turn and no tools (R18): for `task` prompts the output is the model's answer or plan, and the report says that tool use is not exercised. Proof: T.
- R10b. The judge returns JSON (`--json-schema`) with, for every check, `pass` and a **verbatim quote from the output** as evidence. A pass whose quote is empty or blank, or is not found in the output (after whitespace normalisation), counts as a fail; a check the judge omits counts as `unknown` (R24). Output text is wrapped in delimiters and the judge is told it is data. This keeps a candidate from talking the judge into passing everything. Proof: T with hostile outputs.
- R11. Scenarios come from `--examples file.jsonl` (fields `input`, optional `expected`, optional `criteria`; `expected` adds one judged content check "agrees with the reference answer in substance" and each `criteria` string adds one judged check; no regular expressions) or, when absent, from one synthesis call (12 varied inputs or situations including edge cases). With 8 or more scenarios a holdout of at least 3 is kept (split rules in R15) with a fixed seed; fewer than 8 give no holdout, so R3, R12 and R13 cannot be checked and the report says so and returns the original unless `--trust-search` is given; with it, the best candidate is returned only if it beats the original on the valset (with fewer than 8 scenarios every scenario is both dataset and valset, R15), and the result is marked unverified. Proof: T.
- R12. Noise: the original is scored twice on the holdout, on the target model (R14a), as two independent runs (the second is a new call, not served from the disk cache); the win threshold in R3 is `max(0.05, 2 x |difference between the two runs|)`. With a holdout of 3 to 5 scenarios this is a coarse estimate, so the report prints it and the margin by which the winner cleared it. Proof: T.
- R13. If the original already scores at least 0.95 on the holdout, the run stops early and says "already strong, relative to the generated checks" (high scores can also mean weak checks; the report lists the checks so the user can judge). Proof: A.
- R14. The judge model is never the task model and never the target model, compared after aliases (`opus`, `sonnet`, `haiku`), case and a `[1m]` suffix are resolved to full ids: the run that decides the result must not be graded by the model that produced the output. Defaults: task Haiku 4.5, judge Opus 5.5, reflection Opus 5.5, target Sonnet 5.5; when the target is the default judge (for example `/improve` in an Opus session) the default judge is Sonnet 5.5. A choice the user makes that breaks the rule (for example `--judge-model` equal to `--target-model`) exits 2 and names the flag. Models are set with `--task-model`, `--judge-model`, `--reflect-model`, `--target-model`. Proof: T (config validation).
- R14a. Target-model confirmation. The search may use a cheaper task model (default Haiku 4.5; the paper's Obs. 6 shows prompts optimised on a weaker model transfer to a stronger one). The final holdout comparison in R3 is run on the model the user will actually use (`--target-model`, default Sonnet 5.5; the `/improve` command passes the session's model; when it differs from the task model, the report shows both scores). The original (both seed runs of R12) and the finalists are always scored on that same target model, so the two sides of the comparison are like for like. A candidate that wins on the search model and loses or ties on the target model is not returned. Proof: A with `fake`.

### Search
- R15. Search uses `gepa.optimize_anything` with `parallel=False`. Scenarios are split three ways: `dataset` (reflection minibatches), `valset` (acceptance and the Pareto frontier) and the holdout, which the search never sees and which only R3, R12 and R13 use. Split sizes for n scenarios (n >= 8), rounding half up: holdout `min(6, max(3, round(0.35 n)))` (capped at 6 however many scenarios the user supplies, so the fixed costs of R17 stay bounded), valset `clamp(round(0.25 n), 2, 4)`, dataset the rest (never below 3); so n=8 gives 3/2/3, n=10 gives 4/3/3, n=12 gives 4/3/5 and n=40 gives 6/4/30 (holdout/valset/dataset). Below 8 (only with `--trust-search`, R11) there is no holdout and every scenario is both `dataset` and `valset`. `frontier_type="hybrid"` is used (one front per scenario plus one per check group), so a small `valset` still gives a useful frontier. `MergeConfig` is off by default: the paper (Obs. 5, Tables 1-2) found merge helped GPT-4.1 Mini but hurt Qwen3-8B, and its timing is an open question; it may be enabled by `--merge` and is not part of the acceptance measure. Pareto-based selection stays on (paper Table 3: +12.4 points vs +6.1 for best-candidate and +5.1 for beam search). Proof: T on the adapter wiring, A.
- R15a. Validation dominates cost in GEPA (paper Obs. 1: most rollouts go to scoring candidates on the Pareto set), so `valset` is kept small (2 to 4 scenarios) and a candidate is scored on it only after it improves on its minibatch (the library's `strict_improvement` acceptance). Proof: T counts calls on `fake`.
- R16. Reflection receives the contract, the strictness level and per-scenario failed checks with short output excerpts (ASI). Proof: T.

### Budget and safety
- R17. Every `claude -p` call (task, judge, reflection, intake, synthesis) counts toward one budget: default 100, ceiling 300, 45 minutes wall clock (the paper's runs used 400 to 7,000 rollouts, so this tool works in a very low-budget regime where the first few reflective updates carry most of the gain; the report says so). The fixed costs are computed from the plan and shown by `--dry`: before the search, intake, synthesis, two seed runs on the holdout (each a task call per scenario plus one judge call; a judge call covers at most 6 scenarios) and GEPA's scoring of the original on the valset; after it, up to 3 finalists on the target model and up to 3 contract checks (with no holdout: no seed or finalist runs). The search stops when fewer calls are left than one iteration can cost (an accepted child: a reflection, two minibatch passes and a valset pass); a reflection reply that is rejected costs one more call, so the iteration count shown by `--dry` is an estimate, and the hard limit is the call count. The search gets the rest and stops cleanly when it is used up, keeping every candidate it has fully scored, then runs the final steps with the share kept for them; a stop never returns a candidate that skipped R3, R6, R7 or R9. All of this is checked before the first paid call (intake included): if the fixed costs alone exceed the budget the run refuses to start (exit 2). A resumed run (R22) continues the same count and the same clock. The search may use 75 % of the wall clock (monotonic time, carried across `--resume`; a laptop suspend does not count), the final steps the rest; if time runs out before a finalist is confirmed the original is returned. Every call has a 300 s timeout, capped by the clock left; a call is not started when the deadline has passed. Identical calls are cached on disk; a cache hit costs nothing and does not count. Proof: A.
- R18. All model calls go through one function that builds the command `claude -p --safe-mode --tools "" --strict-mcp-config --disable-slash-commands --no-session-persistence --max-turns 1 --model M --output-format json` plus `--system-prompt=<text>` where the call has a system prompt (R10a) and `--json-schema` on intake, synthesis and judge calls, with a scrubbed environment (the proxy and certificate settings a sandboxed shell needs are kept when set, R21); the first live call of every process (a resumed run too) aborts with exit 4 if the session reports plugins, MCP servers or tools, however GEPA handles the error. User text (the prompt, scenarios, model outputs) travels on stdin only (a template candidate, being the system prompt, is the one exception, below); the system prompt is a single `--system-prompt=<text>` argument (the only form), so it cannot be read as an option, has no NUL byte and is at most 100,000 bytes (a longer candidate is rejected as too long before it is run). A template candidate in that argument is visible to other local users in the process list for the length of one call; this is accepted. No API key is read or needed. Details wait for the user's real-call check (BUILD-LOG). Proof: T, S.
- R19. Prompts and model outputs are untrusted data: they are passed as stdin or arguments, never evaluated, never used to build shell commands or file paths. Checks written by a model use fixed kinds only (contains, not_contains, max_chars, min_chars), never regular expressions. `/improve` hands the prompt to the tool through a file, never by interpolating it into a shell line (R21). Proof: T with hostile strings.
- R20. Tests never call a real model or the network. Proof: `just check`.
- R23. Run data (prompt, contract, scenarios, outputs, call cache) is stored under `$XDG_STATE_HOME/autoimprover/runs/<id>/` with mode 0700, never inside a git repository, and `autoimprover clean [<id>]` removes it (exit 0, also when there is nothing to remove). If the state folder is not writable or lies inside a git repository the run exits 2 before any paid call and names `XDG_STATE_HOME`. A run id is the only form `--resume` and `clean` accept (never a path). The prompt is the user's own data, so the report names the folder. Proof: T.
- R24. Failure handling. A call that errors or times out (300 s) is retried up to 2 times (each retry counts toward the budget). A call that still fails is a failed call: inside the search the scenario gets a neutral score and the candidate cannot become a finalist, and a failed reflection call skips that iteration; a failed call while scoring the original is never a 0 either (exit 3 below). A seed run on the holdout that still fails is never scored 0 (that would lower the bar a candidate must beat): the run ends with exit 3, and so does any call that fails outside the search (intake, synthesis, finalist runs, contract checks), because there is no iteration to skip. A judge check that stays `unknown` is excluded from the score; a candidate with more than 30 % unknown checks scores 0 with the reason in its ASI. Three consecutive failed calls of the same kind (task, judge, reflection, ...) to the same model (successes of another kind or model do not reset the count) end the run with exit 3 and the partial run folder kept for `--resume` (R22). A budget stop is not a failure. Proof: A with a failing `fake`.

### Claude Code integration
- R21. `/improve <prompt>` saves the prompt to a file and passes it with `--file` (never inside a shell line), points `XDG_STATE_HOME` at a folder under `$TMPDIR` (outside any git repository) because the command runs in a sandboxed shell where `~/.local/state` is read-only, runs the tool in a background shell call with a timeout above the wall clock (a foreground call is limited to 10 minutes and a run can take 45), deletes the prompt file afterwards, prints the run folder and the `XDG_STATE_HOME` it used so `--resume` and `clean` can be run later, passes the session's model as `--target-model` (R14 picks the fallback judge when that is the default judge), runs the command with `--dry` first when the prompt is longer than 2,000 chars, otherwise runs it directly, shows the report, and then waits for the user's yes before using the improved prompt as the task. `/optimize` is an alias. Proof: S.
- R22. A run can be resumed with `--resume <id>` after an interruption without repeating a successful paid call: the run's prompt, plan, call count and elapsed time are read from its run folder, so a resume never grants a fresh budget or a fresh clock, and a run cut at any point (mid-search, in the last iteration, in the final steps) resumes to the same finalists; a call that failed inside the search is recorded and replayed as failed, so the resume decides as the original did; only the call whose failure ended the run, and failures outside the search, are tried again. Proof: A.

## 3. Non-goals (v1)
Training model weights; multi-prompt pipelines or DSPy programs; the local model at 127.0.0.1:8080 as task model (first follow-up); a hosted service; any network call except `claude -p`.

## 4. Limits
Python 3.12+; one dependency (`gepa==0.1.4`) plus dev tools; one run per run folder (runs with different ids may run together); Max-plan usage is the only cost.

## 5. Acceptance measure (S)
On 8 to 10 of the user's real prompts, the improved prompt is preferred over the original in a blind A/B by the user in at least 70 % of the cases where the tool returned a change (a go/no-go signal, not a statistical proof: 7 of 10 is not significant against chance), with zero contract violations found by the user, a median length ratio at most 1.25 in `conservative`, and the "no reliable improvement" outcome appearing for prompts the user already considers fine. A pairwise Claude judge is reported alongside but does not decide.
